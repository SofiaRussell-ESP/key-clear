Improvement

Case: E-05 - Buried critical finding (EM-02)

Before: CRITICAL_FINDINGS only had to state the finding "plainly" - it could pass by naming a category (e.g. "Subsidence") without pointing to the specific location, measurement, or observation in the document, or saying what to actually do next.

Change: Tightened the CRITICAL_FINDINGS instruction in SYSTEM_PROMPT to require the specific category, the exact supporting detail from the document (precise location/measurement/observation as stated), and the concrete next step - explicitly: "a reader must be able to tell exactly which piece of the document it refers to without re-reading it themselves."

After: "Subsidence / structural - stepped cracking to the brickwork of approximately 3-4mm width at low level beneath the kitchen window to the rear elevation, with some slight distortion to the adjacent door frame, consistent with historic or ongoing subsidence-related movement. Next step: obtain a specialist structural engineer's report to establish the cause and confirm whether remedial works are required."

Known limitations
  • Handles only one buyer's single conveyancing case (Priya Achebe, 14 Thornfield Rise) - not multiple simultaneous transactions or other areas of law.
  • English only - no translation of non-English source correspondence.
  • Processes one email or document at a time, pasted into this exact data structure - there is no inbox integration, batch upload, or file/attachment parsing (PDF, scanned image, etc.).
  • Memory is session-only. Case decisions, the run log, and gate actions reset on reload - only the saved API key and the Evals verdicts/notes persist, in the browser's localStorage. It does not keep the persistent, multi-week running case memory described in the original design.
  • Must-carry finding detection is limited to the six closed categories in must_carry_findings.md - a genuine issue outside that taxonomy (for example, an environmental hazard) is not guaranteed to be flagged.
